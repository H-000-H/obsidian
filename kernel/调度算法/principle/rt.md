# ⚡ RT 实时调度原理（SCHED_FIFO / SCHED_RR）

> [!INFO] 笔记概览
> - **定位**：RT 类解决的不是"平均更快"，而是"**最坏情况可预期**"——它用**静态优先级 + 抢占**换取确定性。本篇讲清它的优先级模型、两种策略（FIFO / RR）、O(1) 选队、同优先级的迁移、以及"防止饿死系统"的节流机制。**本篇只讲原理**，源码落地见 [[linux/rt|Linux RT 实现与注意]]。
> - **内容范围**：什么叫"实时" · 静态优先级模型 · SCHED_FIFO / SCHED_RR 语义 · 位图 + 优先级队列 · 抢占与同优先级处理 · push/pull 迁移 · RT 节流（bandwidth）· 优先级反转与继承 · 与 DL / CFS 的边界
> - **推荐路径**：§1 目标 → §2 优先级模型 → §3 两种策略 → §4 选队结构 → §5 抢占与迁移 → §6 节流 → §7 优先级反转 → §8 边界与误区

## 🎯 1. RT 要解决什么问题

分时调度（[[principle/cfs|CFS]]）追求的是**公平与吞吐**：谁跑得少就让谁跑。但有一类任务关心的是另一件事——**"我最坏要等多久"**：

- 音视频采样、工业控制、机器人闭环、内核里对时延敏感的线程；
- 它们的共同点是：**错过时限的后果不是"慢一点"，而是"功能失效"**。

RT 类的答案很直接：**按固定优先级抢占**。

> [!NOTE] RT 的承诺是"可预期"，不是"更快"
> 一个高优先级 RT 任务只要就绪，就会**立刻**挤掉任何低优先级任务（含普通任务）。它不承诺"平均响应时间更短"，它承诺的是**"不会被低优先级任务拖住"**。这两件事完全不同——前者靠统计，后者靠结构。

## 🧱 2. 静态优先级模型

### 2.1 优先级取值与方向

Linux 用一个统一的**整数优先级 `prio`** 表达所有调度类，约定 **数值越小优先级越高**：

| 区间 | 归属 | 说明 |
|---|---|---|
| `0` | DL | 每个 DL 任务固定为 0（见 [[principle/deadline|截止期调度原理]]） |
| `1 .. 99` | **RT** | 内核侧 RT 优先级区间（`MAX_RT_PRIO = 100`，取值 `< MAX_RT_PRIO`） |
| `100 .. 139` | fair / ext | 由 nice 映射而来（`nice -20..19`） |

用户态看到的是 `sched_priority`：

- **SCHED_FIFO / SCHED_RR** 的合法范围是 **1 .. 99**（0 留给 DL，内核里 DL 与 RT 用不同区间区分）；
- 内核侧换算为 `prio = MAX_RT_PRIO - 1 - rt_priority`，即**用户优先级 99 → 内核 prio 0（最高）**，用户 1 → 内核 prio 98（RT 中最低）。

> [!TIP] 为什么"数字小 = 优先级高"
> 这是 Linux 的历史约定：`prio` 最初就是"队列下标"，下标小的先被取。这个约定贯穿所有调度类，读源码时不要按直觉理解成"数字大 = 高"。

### 2.2 优先级是"静态"的

RT 的优先级由用户（或内核）**显式设定**，不随运行时间、负载、交互性自动调整。调度器**不会**因为某个 RT 任务"跑得多了"就降低它——这正是确定性的来源，也是它的风险来源。

> [!WARNING] 静态优先级 = 没有自动纠偏
> CFS 里"跑多的人自动被排到后面"这种机制，在 RT 里**完全不存在**。一个优先级 99 的 FIFO 任务如果死循环且不让出，它会**永远**占着 CPU（除非节流介入，见 §6）。这是设计取舍，不是 bug。

## 🔀 3. 两种策略：FIFO 与 RR

RT 类对外提供两个 `SCHED_*` 策略，**同优先级**下的行为不同：

| 策略 | 时间片 | 同优先级行为 | 典型用途 |
|---|---|---|---|
| **SCHED_FIFO** | **无**（跑到底） | 后来者**排队尾**，运行者不被同级抢占 | 短小、确定的实时处理 |
| **SCHED_RR** | **有**（默认 100 ms） | 时间片耗尽后**移到同级队尾**，轮转 | 多个同优先级 RT 任务需轮流 |

### 3.1 SCHED_FIFO

- 任务一旦开始运行，就**一直运行到**：主动阻塞（睡眠）、主动 `yield`、或被**更高优先级**任务抢占；
- **同优先级**的新任务就绪时**不会**抢占当前任务，只能排到该优先级的队尾；
- 因此 FIFO 的语义是"**先来先服务 + 严格优先级**"。

### 3.2 SCHED_RR

- 是 FIFO 的"轮转版"：每个任务有**时间片**（内核默认 `RR_TIMESLICE = 100 ms`，可通过 `sched_rr_timeslice_ms` 调整）；
- 时间片**耗尽**后，任务被放到**同优先级队列的队尾**，同级的下一个任务上 CPU；
- 优先级不同的任务之间，仍然是严格的"高优先级先跑"。

> [!NOTE] RR 只在"同级"内轮转
> RR 不是"公平调度"。它只在**同一优先级**的多个任务之间做轮转，跨优先级依旧是抢占。把两个任务设成不同优先级，RR 也救不了低优先级的那个。

### 3.3 `yield` 在 RT 里是什么

`yield()` 对 RT 任务的含义是"**我让出 CPU，排到同级队尾**"。要特别注意它的**陷阱**：

> [!WARNING] 不要用 `yield()` 当"进度保证"
> 内核注释里明确警告：`while (!event) yield();` 这种写法在 **SCHED_FIFO** 下**永远不会**让 `event` 变成 true——因为同级任务不会被 FIFO 的 yield 唤醒去推进。想等待就用 `wait_event()`，想让出就用 `cond_resched()`。
>
> 顺带一提，内核源码对 SCHED_FIFO 有一句很直白的评价：它"**fundamentally incapable of resource management**"，且**无法组合**——两个各自正确的静态优先级工作负载拼在一起，不保证还对。所以它被限制为**特权用户**才能使用。

## 🗂️ 4. 选队结构：位图 + 每优先级一条队列

RT 要做到"**O(1) 选出最高优先级任务**"，靠的是一个非常经典的结构：

```
rt_prio_array
├── bitmap[0..99]        : 每个优先级一个 bit，该优先级有任务则置位
└── queue[0..99]         : 每个优先级一条双向链表（FIFO 顺序）
```

选下一个任务：

1. 在 `bitmap` 上找**第一个置位的 bit**（`sched_find_first_bit`）→ 得到最高优先级 `idx`；
2. 取 `queue[idx]` 的**队首**元素。

两步都是常数时间，且与任务数无关——这就是 RT 调度器"开销低、可预期"的结构基础。

> [!TIP] 位图是"优先级"的自然表达
> 优先级只有 100 档，且需要"取最小者"——这正是位图最擅长的操作（`find_first_bit`）。相比之下 fair 类的键是 64 位 vruntime，只能用红黑树。**选什么数据结构，取决于键的取值空间**。

### 4.1 组调度下会变成一棵"实体树"

启用 `CONFIG_RT_GROUP_SCHED` 后，**任务组本身也作为一个调度实体**参与竞争，于是结构变成**层级**的：

- 每个组有自己的 `rt_rq`（内含 `rt_prio_array`）；
- 一个 `sched_rt_entity` 既代表"组里的任务"，也代表"某个组在父层的入口"；
- 选任务时要**逐层下降**：先在顶层选优先级最高的实体，如果它是个组，就进组内的 `rt_rq` 再选，直到取到真正的任务。

> [!NOTE] 组的"优先级"来自组内
> 组实体在父层的优先级，等于**该组当前最高优先级成员**的优先级。所以一个组里只要有一个高优先级任务，整个组在父层就"顶"到那个高度——这也是层级 RT 调度的关键性质。

## ⚔️ 5. 抢占、同优先级与迁移

### 5.1 抢占时机

RT 的抢占判定非常简单直接：

- **唤醒抢占**：新唤醒任务的优先级**高于**当前任务 → 立刻标记需要重新调度；
- **优先级变更**：任务被 `sched_setscheduler()` 改了优先级后，重新比较；
- **tick**：对 FIFO 任务，tick 只做"看门狗"（RLIMIT_RTTIME 超时告警），**不做**时间片判定；对 RR 任务，tick 负责递减时间片并在耗尽时轮转。

### 5.2 同优先级的麻烦：`check_preempt_equal_prio`

同优先级任务不能抢占，但有一种情况需要**主动腾位置**：

- 新唤醒任务与当前任务**同优先级**；
- 新唤醒任务**不可迁移**（绑定了单个 CPU），而当前任务可迁移。

这时如果"当前任务在下次调度时本来就会被换掉"，内核会尝试**把当前任务推到别的 CPU**，从而给这个不能迁移的任务腾出位置。这是 RT 里"同优先级"唯一需要特殊处理的分支。

### 5.3 迁移：push / pull

RT 任务**不参与 CFS 那套负载均衡**（CFS 均衡的是"负载"，RT 均衡的是"优先级可运行性"）。RT 的迁移靠一对互补机制：

| 机制 | 触发方 | 做什么 |
|---|---|---|
| **push** | 当前 CPU 主动 | 本 CPU 有"多于一个 RT 任务"（**overloaded**）时，把队列里**优先级最低的可迁移**任务推到"**最低优先级 CPU**"上 |
| **pull** | 空闲/低优先级 CPU 主动 | 本 CPU 即将运行一个低优先级任务时，去别的 CPU 拉一个"优先级高于我将要跑的任务"的 RT 任务过来 |

- 判断"是否有资格被推/被拉"用一张**可推列表**：按优先级排序的**可迁移**任务集合；
- "谁最合适接收" = **`lowest_rq`**：在该 CPU 的**根域（root domain）**范围内，找 `highest_prio.curr` 数值最大（即优先级最低）的 CPU；
- 根域维护一个 **overload 掩码 + 计数**，只有被标记 overloaded 的 CPU 才需要被考虑，避免全局扫描。

> [!NOTE] push 与 pull 的分工
> push 解决"**我这里挤不下**"，pull 解决"**我这里有位子但没活干**"。两者都不依赖周期性均衡器——RT 的迁移是**事件驱动**的（入队、让出、优先级变化时排队），因为 RT 任务的等待不能等到下一个均衡周期。

## 🚧 6. RT 节流：防止 RT 任务饿死整个系统

### 6.1 问题

如果没有任何限制，一个优先级 99 的 FIFO 死循环任务会让**普通任务永远得不到 CPU**——连内核线程（如 RCU、workqueue）都跑不了，系统会看起来"假死"。

### 6.2 模型：周期 + 配额

RT 节流用一个**带宽模型**兜底，参数在**每个根域**上：

| 参数 | 含义 | 默认 |
|---|---|---|
| `rt_period` | 统计周期 | 1 s |
| `rt_runtime` | 一个周期内 RT 任务**最多**能用的时间 | 见下 |

规则：每个周期开始，`rt_time` 清零；运行期间累加；当 `rt_time` 超过 `rt_runtime` → **throttle**（把该 `rt_rq` 从"顶层可运行"摘掉，RT 任务暂时不参与调度），直到**下一个周期**再恢复。

> [!WARNING] 本基线默认"不节流"
> 本基线（7.3.0-rc6）源码里 `sched_rt_period_us` 与 `sched_rt_runtime_us` 的默认值**都是 1 000 000（1 s）**。而判定逻辑是"`runtime >= period` 就直接不检查"，所以**默认等于关闭节流**——RT 任务可以吃满 CPU。
>
> 历史版本（≤ 6.x）默认 `runtime = 950 000`，即**保留 5%** 给非 RT 任务。把 `sched_rt_runtime_us` 写成 **-1** 表示完全不限制（`rt_bandwidth_enabled()` 返回 false）。
>
> 生产环境若要在 RT 与普通任务间共存，通常**应显式设置** `sched_rt_runtime_us`。

### 6.3 共享与借用

- **RT_RUNTIME_SHARE**：允许 CPU 之间**借用**空闲的 RT 配额——某 CPU 用超时，可以从根域内其它"有富余"的 CPU 各借 `1/n`（上限为本周期）；
- **组调度**下每个组也有自己的 `rt_bandwidth`，可以给不同 cgroup 设不同的 RT 配额。

> [!TIP] 节流 ≠ 公平
> 节流只是"**别把系统饿死**"的保险丝，它**不**在 RT 任务之间做公平分配。RT 任务之间的秩序仍由优先级决定。

## 🔄 7. 优先级反转与优先级继承

### 7.1 问题：优先级反转

经典场景（火星探路者事故同款）：

- 低优先级任务 **L** 持有锁 M；
- 高优先级任务 **H** 需要 M，被阻塞；
- 中优先级任务 **M**（与锁无关）把 **L** 抢占 → **L 无法释放锁 → H 无限等待**。

结果是"**中优先级实际跑赢了高优先级**"——优先级语义被彻底破坏。

### 7.2 解法：优先级继承（PI）

内核的 **rt_mutex** 实现了优先级继承：当 H 阻塞在 L 持有的 rt_mutex 上时，**临时把 L 的优先级提升到 H 的优先级**，让 L 尽快跑完、释放锁，然后恢复 L 的原优先级。

- 这解释了为什么"任务的有效优先级"可能**不等于**它被设定的优先级——**PI 提升**会临时改写它；
- 因此源码里判断"是不是 RT 任务"有两个层次：看**当前有效优先级**（含 PI 提升），还是看**原始策略**（不含 PI）。

> [!NOTE] 与 CFS 的 futex PI 对照
> 优先级继承是**实时语义**的核心组成部分。没有它，静态优先级就形同虚设。CFS 侧对应的机制是 PI-futex（`rt_mutex` 也用于普通 futex 的 PI 路径）。

## 🧭 8. 边界与常见误区

### 8.1 RT ≠ 硬实时

| 维度 | RT（SCHED_FIFO/RR） | DL（SCHED_DEADLINE） |
|---|---|---|
| 表达什么 | **优先级** | **截止期** $(runtime, deadline, period)$ |
| 时限保证 | **无**（只保证"不被低优先级拖住"） | **有**（可证明的截止期满足） |
| 准入控制 | **无**（谁都能设，只要特权） | **有**（带宽准入，超了直接拒绝） |
| 超载行为 | 优先级低的**饥饿** | 被 CBS 隔离，不产生连锁 |

> [!WARNING] 名字像，承诺不同
> RT 只提供"**优先级抢占**"这一件事。要"可证明的时限"，用 [[principle/deadline|SCHED_DEADLINE]]。把 RT 当硬实时用，是常见的误解。

### 8.2 与其它调度类的关系

- **层级**：`stop > dl > rt > fair > ext > idle`。RT 在 DL 之下、fair 之上；
- 只要有一个 RT 任务可运行，fair / ext / idle 的任务**一个都跑不了**；
- RT 任务**仍然会被 DL 任务和 STOP 任务抢占**。

### 8.3 实践清单

> [!WARNING] 使用 RT 的注意事项
> 1. **RT 是特权**：默认需要 `CAP_SYS_NICE` 或 `RLIMIT_RTPRIO`（否则 `sched_setscheduler` 返回 `EPERM`）；
> 2. **RT 任务必须会阻塞**：靠"事件驱动 + 睡眠"来让出 CPU，不能靠时间片（FIFO 没有时间片）；
> 3. **别用 `yield()` 当进度保证**（见 §3.3）；
> 4. **注意优先级反转**：共享锁时用 rt_mutex / PI 语义；
> 5. **显式配置节流**：否则一个死循环 RT 任务能锁死系统；
> 6. **不要设太多优先级档位**：静态优先级"不可组合"，层级越多越难推理。

---

## 🧭 一句话总结

> **RT = 静态优先级 + 严格抢占：用位图与"每优先级一条队列"实现 O(1) 选最高优先级任务，FIFO 无时间片（跑到底、同级排队尾），RR 有时间片（同级轮转）；靠 push/pull 做事件驱动的迁移，靠周期/配额节流兜底防止饿死系统，靠优先级继承对抗优先级反转。它承诺"不被低优先级拖住"，但不承诺截止期——那是 DL 的事。**
