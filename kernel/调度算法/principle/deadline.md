# ⏳ 截止期调度原理（Deadline Scheduling）

> [!INFO] 笔记概览
> - **定位**：讲清"截止期调度"这一类**动态优先级实时调度**要解决什么问题、靠什么模型给出**可证明的截止期保证**。**本篇只讲原理**（不绑定任何具体内核），Linux 落地细节见 [[linux/deadline|Linux DL（`SCHED_DEADLINE`）实现与注意]]。
> - **内容范围**：实时任务模型 · EDF 最优性与可调度性 · EDF 的两个弱点 · CBS 带宽服务器 · GRUB 带宽回收 · 准入控制 · 运行时行为 · Linux `SCHED_DEADLINE` 对照 · 常见误区
> - **推荐路径**：§1 任务模型 → §2 EDF → §3 CBS → §4 GRUB → §5 准入 → §6 运行时 → §7 工业实现 → §9 误区

---

## 0. 一句话

截止期调度是一类**动态优先级实时调度**：任务的优先级不再是固定数字，而是由**绝对截止期（absolute deadline）**动态决定——**谁最紧急（截止期最早）谁先跑**。它的目标不是"排得靠前"，而是**可证明地保证每个任务在截止期前完成**。

---

## 1. 实时任务模型

### 1.1 参数

一个周期性实时任务 $\tau_i$ 由以下参数描述：

| 符号 | 名称 | 含义 |
|---|---|---|
| $C_i$ | 最坏执行时间 WCET | 每次释放最多需要多少 CPU 时间 |
| $T_i$ | 周期 | 每隔多久释放一次 |
| $D_i$ | 相对截止期 | 从释放时刻起，必须在此之内完成 |
| $d_{i,k}$ | 绝对截止期 | 第 $k$ 次释放的绝对时刻 $d_{i,k} = r_{i,k} + D_i$ |
| $\phi_i$ | 相位 | 首次释放时刻 |

工程实现上通常用三个量来表达（如 Linux `SCHED_DEADLINE`）：

- **runtime（预算 $Q$）**：每个周期最多能消耗的 CPU 时间，是 $C_i$ 的上界。
- **deadline（相对截止期 $D$）**：每个周期内必须完成的时限。
- **period（周期 $P$）**：多久补充一次预算。

**约束**：

$$0 < Q \le D \le P$$

- $Q \le D$：预算不能超过时限，否则必然错过。
- $D \le P$：时限不能超过周期，否则本轮还没到期、下一轮已经开始。

> **runtime 是上限（cap），不是目标**。任务应在预算耗尽之前主动让出 CPU（表示本轮完成）。

### 1.2 截止期的三种类型

| 类型 | 关系 | 说明 |
|---|---|---|
| 隐式截止期 implicit | $D = T$ | 最简单，判据最干净 |
| 约束截止期 constrained | $D \le T$ | 常见；判据需要更严格 |
| 任意截止期 arbitrary | $D > T$ | 最复杂，同一任务可能重叠多个作业 |

### 1.3 利用率与密度

$$U_i = \frac{C_i}{T_i}, \qquad U = \sum_i U_i \quad(\text{总利用率})$$

$$\delta_i = \frac{C_i}{\min(D_i,\, T_i)}, \qquad \delta = \sum_i \delta_i \quad(\text{总密度})$$

利用率衡量"长期 CPU 占用比例"，密度衡量"短期紧迫程度"。当 $D_i = T_i$ 时二者相等。

### 1.4 实时的三个层次

- **硬实时 hard**：错过截止期 = 系统失败，不可接受。
- **固实时 firm**：错过 = 结果无价值，但不致命。
- **软实时 soft**：错过 = 质量下降，可接受（音视频丢帧）。

## 2. 动态优先级：EDF

### 2.1 定义

**Earliest Deadline First（最早截止期优先）**：在任意时刻，选择**绝对截止期最早**的就绪作业执行。

- 优先级是**动态**的：每次作业释放/完成都会改变。
- 抢占式：新释放的作业若截止期更早，立即抢占当前作业。

### 2.2 最优性定理

> **定理**：在单处理器、抢占式的前提下，若存在任何调度算法能使一组约束截止期任务满足所有截止期，则 **EDF 也能**。

EDF 是**单处理器抢占式调度的最优算法**。

⚠️ 边界条件：
- 仅在**单核**上最优。多核上全局 EDF 不是最优的（充分利用率界约为 $m - (m-1)U_{\max}$，其中 $m$ 为核数、$U_{\max}$ 为单个任务的最大利用率）。
- 非抢占式、或存在任意释放抖动时，最优性不再成立。

### 2.3 可调度性判据

**隐式截止期（$D_i = T_i$）**：

$$U = \sum_i \frac{C_i}{T_i} \le 1$$

这是**充要条件**：$U \le 1 \iff$ EDF 可调度。

**约束截止期（$D_i \le T_i$）**：

利用率判据不再充分。精确判据是**处理器需求判据（Processor Demand Criterion, PDC）**（Baruah, Rosier, Howell, 1990）：

$$\forall L > 0:\quad \sum_i \max\!\left(0,\ \left\lfloor \frac{L - D_i}{T_i} \right\rfloor + 1\right) C_i \ \le\ L$$

直观含义：**任意长度 $L$ 的区间内，所有任务累积的截止期需求不超过 $L$**。实际只需检查 $L$ 取值为各 $D_i$ 与 $D_i + kT_i$ 构成的有限集合。

**充分条件（更易用）**——密度判据：

$$\delta = \sum_i \frac{C_i}{\min(D_i,\, T_i)} \le 1 \ \Longrightarrow\ \text{可调度}$$

### 2.4 与固定优先级对比（RM / DM）

| | RM（速率单调） | DM（截止期单调） | EDF |
|---|---|---|---|
| 优先级依据 | 周期越短越高 | 相对截止期越短越高 | 绝对截止期最早 |
| 优先级 | 静态 | 静态 | **动态** |
| 最优性 | 固定优先级中非最优 | **固定优先级中最优** | **全局最优（单核）** |
| 充分判据 | $U \le n(2^{1/n}-1)$ | 用 RTA | $U \le 1$（$D=T$） |
| 利用率上限 | 约 69%（最坏情形） | 约 69% | **100%** |
| 实现复杂度 | 低（查表 / 位图） | 低 | 高（需按截止期排序） |

**RM 的充分利用率界**：

$$U \le n\left(2^{1/n} - 1\right), \qquad n \to \infty \ \Rightarrow\ \ln 2 \approx 0.693$$

另有更紧的**双曲界**：$\prod_i (U_i + 1) \le 2$。

**RM / DM 的精确判据**是响应时间分析（RTA）：

$$R_i = C_i + \sum_{j \in hp(i)} \left\lceil \frac{R_i}{T_j} \right\rceil C_j$$

迭代至收敛；可调度 $\iff R_i \le D_i \ (\forall i)$。

**结论**：EDF 的理论天花板更高（100% vs 69%），但实现更贵、行为更"脆弱"。

### 2.5 EDF 的两个致命弱点

1. **无隔离（no isolation）**：EDF 不区分任务。一个任务超支会**连锁**导致其他任务也错过截止期——称为 **domino effect（多米诺效应）**。利用率越接近 1 越危险。
2. **超载时行为不可预测**：当 $U > 1$，EDF 无法保证任何任务——可能连最关键的任务也崩。

→ 这两个弱点直接催生了**带宽服务器（CBS）**。

## 3. 带宽服务器：CBS

### 3.1 动机

把"任务"抽象成一个**服务器**，服务器对外只承诺一件事：**每 $P$ 时间给你 $Q$ 的 CPU 时间**。于是：

- 服务器内部怎么用不管；
- 服务器之间**互相隔离**（一个超支不会拖垮别人）；
- 用 $(Q, P)$ 描述，可以直接做准入判断。

### 3.2 定义

**Constant Bandwidth Server（固定带宽服务器）**：服务器 $S$ 由 $(Q, P)$ 定义，其带宽为

$$U_S = \frac{Q}{P}$$

服务器状态记为 $(c, d)$：$c$ = 当前剩余预算，$d$ = 当前截止期。

### 3.3 核心规则

1. **执行**：服务器被调度执行 $\Delta t$ → $c \leftarrow c - \Delta t$。
2. **补充（replenishment）**：到达周期边界 → $c \leftarrow Q$，$d \leftarrow d + P$。
3. **节流（throttle）**：$c = 0$ → 服务器**禁止执行**，直到下一个周期边界。
4. **空闲（idle）**：服务器无待处理作业 → 变为 inactive，其带宽从活跃集合中移除。

**关键性质**：无论内部如何执行，服务器长期占用的 CPU 不超过 $U_S = Q/P$。

### 3.4 截止期是否顺延：两种变体

这是 CBS 最重要的设计选择：

| 变体 | 预算耗尽时 | 后果 | 适用 |
|---|---|---|---|
| **不推迟 non-deferrable** | $d$ 保持不变 | 到 $d$ 未完成 = **deadline miss**，显式报错 | **硬实时** |
| **推迟 deferrable** | $d \leftarrow d + P$ | 任务跨周期继续，不报错 | 软实时 |

**Linux `SCHED_DEADLINE` 采用不推迟**：截止期按周期固定推进，预算耗尽 → throttle，到截止期仍未完成即视为错过。

> 直觉：硬实时要的是"**承诺 + 可见的违规**"，而不是"永远不报错"。推迟截止期会把"任务超支"这个事实静默掩盖掉。

### 3.5 状态机

```
             作业释放
                 │
                 ▼
        ┌─────────────────┐
        │  ACTIVE  c > 0  │◄──────────────┐
        └───┬─────────┬───┘               │
   执行消耗 │         │ c 耗尽            │ 周期边界
            ▼         ▼                   │ c←Q, d←d+P
      ┌─────────┐  ┌─────────────┐        │
      │运行/就绪│  │ THROTTLED   │────────┘
      └─────────┘  │   c = 0     │
                   └─────────────┘
     无待处理作业 → INACTIVE，释放带宽
```

## 4. GRUB：带宽回收

### 4.1 问题

CBS 的一个缺陷：**任务阻塞时，它的带宽被白白浪费**。

例：两个服务器 $S_1(U=0.3)$、$S_2(U=0.4)$，总带宽 0.7。若 $S_1$ 长时间阻塞，CPU 只用 40%——剩下 60% 空闲，而 $S_2$ 仍然只能拿 40%。

### 4.2 核心思想

**Greedy Reclamation of Unused Bandwidth（贪婪回收空闲带宽）**：把阻塞服务器"让出"的带宽，**按比例转移**给还在跑的服务器。

需要三个带宽量（与 Linux 记账名称对照）：

| Linux 名称 | 含义 | 本节记号 |
|---|---|---|
| `running_bw` | **活跃**（就绪 / 运行中）任务带宽之和 | $U_{\text{act}}$ |
| `this_bw` | 该 runqueue 上**全部**任务带宽之和（含非活跃） | $U_{\text{total}}$ |
| `max_bw` | DL 任务可用的**最大**带宽（受 RT throttling 限制） | $U_{\max}$ |

- $U_{\text{act}}$ 随阻塞 / 唤醒**实时变化**；
- $U_{\text{total}}$ 只在**准入 / 释放**时变化，**阻塞不改变它**。

> **关键细节：0-lag time（延迟回收）**。任务阻塞时带宽**不会立即回收**——立即回收会破坏其他任务已经作出的截止期承诺。内核让任务先进入 `ActiveNonContending` 过渡态，并启动"失效定时器"，直到 **0-lag 时刻**才把带宽从 `running_bw` 移除：
> $$t_0 = d - \frac{c}{U}, \qquad U = \frac{Q}{P}$$
> 其中 $c$ 为剩余预算、$d$ 为当前截止期。若任务在 $t_0$ 前醒来，则取消定时器，带宽照旧保留。

### 4.3 预算消耗速率

活跃服务器执行时，预算**不再按 1:1 消耗**。Linux 的精确公式是：

$$\frac{dq}{dt} = -\,\frac{\max\{\,U_i,\ U_{\max} - U_{\text{inact}} - U_{\text{extra}}\,\}}{U_{\max}}, \qquad U_{\text{inact}} = U_{\text{total}} - U_{\text{act}}$$

在"全部已准入、无额外回收（$U_{\text{extra}} = 0$）"的常见情形下 $U_{\text{inact}} = U_{\max} - U_{\text{act}}$，且 $U_i \le U_{\text{act}}$，于是简化为：

$$\text{消耗速率} = \frac{U_{\text{act}}}{U_{\max}}$$

**效果**：

- 全部活跃（$U_{\text{act}} = U_{\max}$）→ 速率 = 1，预算按真实时间消耗。
- 部分阻塞（$U_{\text{act}} < U_{\max}$）→ 速率 < 1，预算**消耗变慢** → 在跑的任务"借"到了阻塞者的份额。

**推论**：若只有一个服务器活跃，其预算能支撑 $P \cdot U_{\max}$ 的真实时间，即它最多能拿到 $U_{\max}$ 的 CPU——**回收上限就是准入总带宽**。

### 4.4 为什么必须是全局比例

因为所有服务器共享同一个 CPU，可调度性分析是以**全体带宽和**为单位的。若让每个服务器"各算各的预算"，就破坏了"共享池"前提，EDF 的"$U \le 1 \Rightarrow$ 不 miss"不再成立。

> 记账要点：$U_{\text{total}}$（准入总带宽）只在**准入 / 释放**时变化，**阻塞不改变它**；$U_{\text{act}}$ 随阻塞 / 唤醒变化，但阻塞的影响要**经过 0-lag 延迟**才真正体现在 $U_{\text{act}}$ 上。

## 5. 准入控制（Admission Control）

### 5.1 为什么必须

EDF / CBS 的可调度性保证**只在总量不超载时成立**。因此新任务加入前必须先算账：**加进来会不会超？** 会就拒绝。

### 5.2 测试

$$\sum_i \frac{Q_i}{P_i} \le U_{\text{cap}}$$

- 隐式截止期下，理论极限是 $U_{\text{cap}} = 1$。
- 工程上留余量：**Linux 与多数实现取 95%**，剩下的留给内核维护、中断与 idle。

> 注意：$Q/P$ 只是**利用率**判据。当 $D < P$ 时，它还不足以证明可调度，需要更严的**密度判据** $\sum Q_i/D_i \le 1$ 或处理器需求判据。以 $Q/P$ 做准入在 $D < P$ 时是**偏乐观**的。

### 5.3 拒绝策略

准入失败 → **拒绝创建**（返回错误），而不是"先放进来再说"。这是硬实时系统能给出保证的前提。

## 6. 运行时行为总结

| 事件 | 内核动作 |
|---|---|
| 每个 tick | 按 $U_{\text{act}} / U_{\max}$ 扣减运行中服务器的预算 |
| 预算耗尽 | **throttle**：踢下 CPU，停到截止期 |
| 到达截止期 | **补充**：预算重置为 $Q$，截止期 $+= P$ |
| 截止期到但未完成 | **deadline miss**：计数 + 回调（通常不杀任务） |
| 任务主动阻塞 | 进入 `ActiveNonContending` 过渡态；到 **0-lag 时刻**才移出活跃集合（$U_{\text{act}}$ 减少） |
| 任务唤醒 | 重新进入活跃集合（$U_{\text{act}}$ 增加） |
| 任务销毁 | **归还带宽**（$U_{\text{total}}$ 减少），否则永久泄漏 |

**要避免 miss，任务必须**：

1. 预算留足余量（$Q$ 严格大于实际 WCET）；
2. 在截止期前**主动阻塞**（表示本轮完成）。

否则：预算耗尽 → throttle → 到截止期仍被节流 → 必然 miss。

## 7. 工业实现：Linux `SCHED_DEADLINE`

- **引入**：Linux 3.14（2014），基于 CBS + GRUB。
- **参数**（`sched_setattr(2)`，单位 ns）：
  - `sched_runtime` = $Q$
  - `sched_deadline` = $D$
  - `sched_period` = $P$（为 0 时取 $D$）
  - 约束：`runtime ≤ deadline ≤ period`
- **调度类优先级**：**最高**，压过 `SCHED_FIFO` / `SCHED_RR` / CFS。
- **准入控制**：总带宽默认上限 **95%**；超出时 `sched_setattr` 返回 `EBUSY`。
- **截止期不推迟**：预算耗尽 → throttled，直到下一个周期边界；本周期未完成不会自动顺延（视为错过）。
- **GRUB 回收**：4.13 之后加入（按 root domain 控制）。
- **典型用法**：

```bash
# runtime=1ms, deadline=period=5ms  → 带宽 20%
chrt -d --sched-runtime 1000000 --sched-deadline 5000000 --sched-period 5000000 0 ./app
```

- **cgroup**：`cpu.max` 等接口可对 DL 任务做带宽约束；DL 带宽在 cgroup 中单独核算。

## 8. 与固定优先级 RTOS 的对比

| 维度 | 固定优先级（FreeRTOS 等） | 截止期调度（EDF + CBS） |
|---|---|---|
| 优先级 | 静态数字 | **动态（绝对截止期）** |
| 保证 | 相对（谁先跑） | **绝对（截止期前完成）** |
| 隔离 | 有（按优先级） | 需 CBS 才**有** |
| 利用率上限 | 约 69%（RM 充分判据） | **100%**（$D=T$） |
| 超载行为 | 低优先级饿死（可预测） | **domino effect（不可预测）** |
| 准入控制 | 无 | **有（带宽税）** |
| 实现成本 | 低（位图 + 就绪链） | 高（排序 + 记账 + 时间轮） |
| 典型场景 | 一般 RTOS、控制 | 硬实时、多媒体、混合关键级 |

**本质区别**：固定优先级回答"**谁先跑**"；截止期调度回答"**能不能按时跑完**"——后者是更强的承诺。

## 9. 常见误区

1. **deadline = period？** 不必然。$D \le P$，很多场景 $D < P$（"周期前半段必须完成"）。$D = P$ 只是特例。
2. **runtime 是目标？** 不是，是**上限**。把预算用满 = 超支 = throttle = miss。
3. **预算耗尽 = 完成任务？** 不是。耗尽只说明"额度用完了"，任务未必完成。
4. **阻塞 = 释放带宽？** 不。阻塞只把服务器移出**活跃集合**（$U_{\text{act}}$，且要经 0-lag 延迟），**准入份额（$U_{\text{total}}$）仍被占着**，只有销毁才归还。
5. **deadline 可以随便改？** 通常不行（Linux 需重建任务；内核实现往往直接禁止），因为截止期是承诺。
6. **EDF 总是比 RM 好？** 理论上利用率更高，但实现更贵、超载时更脆弱。简单系统用 RM 往往更稳。
7. **多核上 EDF 也最优？** 不。单核最优；多核全局 EDF 有利用率损失。

---

## 10. 一句话总结

> **截止期调度 = 用"绝对截止期"当优先级（EDF，单核最优），用"带宽服务器"（CBS）给每个任务圈定 CPU 份额，用"带宽回收"（GRUB）把空闲份额转给在跑的任务，用"准入控制"保证总量不超载。**
>
> 它比固定优先级多给了一个**可证明的绝对承诺**：到截止期前一定拿到约定的 CPU。代价是实现复杂、超载时脆弱，并且必须靠准入控制兜底。
